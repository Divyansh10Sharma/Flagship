Flagship Deck log · 14 legs

Leg 00 · Orientation

How to read this log

A record of building Flagship — what we decided, what broke, and what the things we did are actually called.

Flagship is a daily flag-guessing game. Everyone in the world gets the same three flags each day, you get three attempts at each, and your streak multiplies your score. It is about 3,400 lines of TypeScript, and it took roughly a dozen distinct pushes to build.

This log walks those pushes in order. It is written for someone who wants to understand why each decision was made, not just what the final code looks like.

Every leg has the same three beats

You asked for the concept first and the vocabulary second, so each leg is built that way, and the three voices look different on the page so you can skim for the one you want:

Leg 01 · Foundations

The scaffold

Choosing the tools before there is anything to build with them.

Before we started

The question at the beginning of any project is not "which framework" but "what does this thing actually have to do?" Flagship has to: show a flag, take a guess, keep score, remember you tomorrow, and work on a phone with bad reception. Nothing about that needs a server rendering pages. It is a small, interactive, self-contained app.

That answer picks the tools for you.

In plain words

Browsers only really understand HTML, CSS and JavaScript. We wanted to write in a nicer language and split the code across forty files, so we needed a program that takes all our files and squashes them into something a browser can load quickly. That program is Vite. It also watches your files while you work and updates the page instantly when you save.

The stack, and the actual reason for each piece:

Stack and rationale
PieceWhy this one
ViteInstant dev server, one command to produce a deployable folder. No server-side rendering needed for a game with no SEO surface.
React 18The screen is a function of the game state. React is the least surprising way to express that.
TypeScriptA country has a code, a name, a tier. Writing that down once means the editor catches a typo before the browser does.
Tailwind v4Styles live next to the markup they style. v4 needs no config file — the design tokens go straight in the CSS.
MotionAnimation that survives a component unmounting, which plain CSS cannot do.
SupabaseA hosted Postgres with authentication attached. Accounts and a leaderboard without writing a backend.

The build order mattered as much as the choices. The plan sequenced it so that the app was fully playable as a guest before authentication, syncing, or any styling was attempted. That is deliberate: if you run out of time or energy, you want the thing that already exists to be a working game, not a beautifully-styled login screen with no game behind it.

The terms for it

Build tool / bundler — the program that turns many source files into few browser-ready ones. Transpiling — converting TypeScript into JavaScript. Hot module replacement (HMR) — swapping changed code into the running page without a refresh. Vertical slice — building one complete path through the app end to end before widening, which is what "playable before pretty" describes.

Leg 02 · Data

When the data source is dead

The plan named an API. The API no longer existed.

Before we started

A flag game needs a list of countries: name, two-letter code, flag image, capital, region, population. The plan said to fetch it from restcountries.com once at build time and save the result as a JSON file in the repo.

That instinct — fetch once, commit the result — is worth pausing on, because it is the single best decision in the data layer.

In plain words

There are two ways to get the country list. Ask a website for it every time a player opens the game, or ask once on your own machine, save the answer into the project, and ship that. The second way means the game still works if that website is slow, down, or gone. It also means the list can never change under you.

The first way is a dependency on someone else's uptime, forever. The second is a file.

Which turned out to be prophetic, because:

Symptom
The fetch script returned {success: false} for every request.
Cause
restcountries.com had shut down its free tiers. Versions 1 through 4 were dead; v5 required an account and an API key. The plan was written against an API that no longer existed.
Fix

Rebuild the dataset from its own upstream sources instead of a middleman:

  • mledoze/countries on GitHub — the dataset restcountries was itself built from
  • World Bank API — current population figures
  • flagcdn — flag images by country code

The output shape is byte-for-byte what the plan specified, so nothing downstream knew the difference.

Because the failure was permanent and the reasoning would be invisible to anyone reading the script later, the explanation went into the file itself:

scripts/fetch-countries.mjs

// NOTE ON THE SOURCE: the plan called for restcountries.com/v3.1. That API
// was shut down — v1..v4 now return {success:false} for every request, and
// v5 requires an account API key. This script uses the same underlying
// dataset restcountries was built from (mledoze/countries) plus World Bank
// population, and produces the identical output shape the plan specifies.

A comment that explains a decision is worth ten that explain syntax. The next person to open that file will otherwise waste an afternoon wondering why it doesn't use the obvious API.

Difficulty came free

Each country got a tier from 1 to 3, derived from population and land area — the reasoning being that people recognise flags of countries they hear about. The split landed at 64 / 61 / 70, close enough to even that no hand-tuning was needed. Each daily round pulls one from each tier in order, so every day ramps from easy to hard.

The terms for it

Build-time data versus runtime data — resolved once when you build, versus fetched while the user waits. Vendoring — committing a copy of an external dependency into your own repository so you control it. Upstream — the original source a dataset or package derives from. Third-party dependency risk — the thing that just bit us.

Leg 03 · Determinism

The same three flags for everyone

The trick at the heart of every daily puzzle game, and it needs no server.

Before we started

Everyone must get the same flags on the same day, or there is nothing to talk about and no reason to come back. The obvious solution is a server that decides each day's flags and hands them out. That means running a server, paying for it, and having the game break when it is down.

There is a much better way, and it is the single most elegant idea in this codebase.

In plain words

Computers can't really make random numbers. They run a formula that looks random. Feed the same starting number in and you get the same "random" sequence out — every time, on every device, forever.

So: turn today's date into a number. Use it as the starting number. Now every phone on earth independently calculates the same three flags, with no server and no coordination. Tomorrow's date gives a different number, and different flags.

Two small functions do all of it. The first turns the string "2026-09-03" into a number:

src/lib/daily.ts

/** FNV-1a, uint32. */
export function hashString(s: string): number {
  let h = 2166136261;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return h >>> 0;
}

The second takes that number and produces a repeatable stream of values between 0 and 1:

export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return function () {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

And the whole daily-rounds feature is four lines:

const POOLS = [byTier(1), byTier(2), byTier(3)];

export function getDailyRounds(dateKey: string): string[] {
  const rand = mulberry32(hashString(dateKey));
  return POOLS.map((pool) => pool[Math.floor(rand() * pool.length)].code);
}

The hidden requirement

This only works if the pools are in the same order on every device. If one phone sorted the country list differently, the same seed would select a different country. So the data file is sorted by country code at generation time and never re-sorted at runtime. There is a comment in the source saying exactly that, because it is the kind of invariant someone breaks by accident six months later while adding a feature.

The terms for it

Deterministic — same input, same output, always. Seeded PRNG (pseudo-random number generator) — the formula above; pseudo is doing real work in that name. Hash function — turns arbitrary data into a fixed-size number; FNV-1a is a fast non-cryptographic one. Invariant — a condition the code assumes is always true, like the sort order. Pure function — depends only on its arguments and touches nothing else, which is why this is trivial to test.

Leg 04 · State

Scoring, streaks, and not losing progress

Rules as plain functions, and a save file that survives you closing the tab mid-round.

Before we started

Game rules and screen drawing are two different jobs, and mixing them is how codebases rot. So the rules were written first, as ordinary functions with no React in them at all — no components, no hooks, nothing about the display. They take numbers and return numbers.

src/lib/scoring.ts

export const POINTS_BY_ATTEMPT = [5, 3, 1]; // index = attempt - 1

/** Streak includes today. */
export function multiplierFor(streak: number): number {
  if (streak >= 30) return 2;
  if (streak >= 14) return 1.75;
  if (streak >= 7)  return 1.5;
  if (streak >= 4)  return 1.25;
  if (streak >= 2)  return 1.1;
  return 1;
}

You can read the entire economy of the game in twelve lines, and you can test it without rendering anything.

Local first, account second

In plain words

The game saves everything to your own browser's storage the instant it happens. No account needed, no network needed. Signing in is a bonus that copies your history to a server so it follows you to another device.

Built the other way round — server first, browser as a cache — the game would be unplayable on a train.

Two details make this actually robust rather than nominally robust:

The save file has a version number. If the shape of the saved data ever changes, old saves would crash the new code. So the version is stored alongside the data; on load, a mismatch wipes and starts fresh rather than trying to read a structure that no longer exists.

Corrupt data is expected, not exceptional. Anyone can open devtools and put garbage in local storage. Reading it is wrapped so that unparseable data resets the save instead of white-screening the app. Both paths are covered by tests — "corrupt localStorage resets instead of white-screening" is a named, passing check.

Progress is written after every single guess and again when the tab is hidden, so closing the browser mid-round loses nothing. The resume logic was tested at four separate points: mid-round-one, after a wrong guess, during a reveal, and after the third round but before the results screen renders.

The terms for it

Local-first (or offline-first) — the device is the source of truth, the server is the backup. Separation of concerns — rules and rendering in different files. Schema versioning and migration — the version number on the save file. Defensive parsing — assuming stored data is hostile. Graceful degradation — full function without a network.

Leg 05 · Search

Two hundred countries in a text box

The most-used control in the app, and the one with the subtlest bug.

Before we started

Every guess goes through one control, so it gets more use than everything else combined. It has to handle real typing: abbreviations (uae), alternative names (holland), accents (côte d'ivoire), and partial words.

The approach: normalise everything (lowercase, strip accents), give countries a list of aliases, and rank matches so the likeliest is first.

In plain words

Not all matches are equal. If you type "ind", India should beat British Indian Ocean Territory — both contain the letters, but one starts with them. So matches get sorted into buckets: names that start with what you typed come before names that merely contain it.

Then this happened:

Symptom
Typing uk put Ukraine at the top instead of the United Kingdom.
Cause
"Ukraine" literally starts with the letters u-k, so it landed in the high-priority "starts with" bucket. "uk" for the United Kingdom was only an alias, which ranked lower. The ranking was working perfectly and producing the wrong answer.
Fix
Add a bucket above "starts with": an alias typed in full wins outright. "uk" is a complete alias for the UK, so it beats a prefix match on Ukraine. A partial alias still ranks normally.

src/lib/search.ts

const exactName: Country[] = [];
const exactAlias: Country[] = [];
const starts: Country[] = [];
const contains: Country[] = [];

// An alias typed in full wins outright, otherwise "uk" lands on Ukraine.
if (key === q) { exactName.push(c); continue; }
if (aliases?.includes(q)) { exactAlias.push(c); continue; }
// ...

return exactName.concat(exactAlias, starts, contains);

One alias was also deleted rather than fixed: ZA: ["sa"] for South Africa. "sa" is a plausible abbreviation for Saudi Arabia too, and an ambiguous shortcut that silently picks one is worse than no shortcut at all — you lose an attempt to a guess you did not make.

The terms for it

Normalisation — reducing input to a canonical form before comparing. Ranking / relevance tiers — the buckets. Prefix match versus substring match. Fuzzy search — the general family this belongs to. Stable sort — why each bucket stays alphabetical: the input list already was, and concatenating preserves it.

Leg 06 · Backend

Accounts, and who is allowed to read what

A leaderboard is a database that strangers read. That is a security question, not a feature.

Before we started

Adding accounts introduces the first genuinely dangerous surface in the project. Up to here, the worst a malicious user could do was cheat their own score. Now there is a shared database.

Supabase puts a real Postgres database behind a JavaScript client — the browser talks to the database more or less directly. That is only safe because of one mechanism.

In plain words

Normally a server sits between the browser and the database and decides what each person is allowed to see. Here there is no such server. Instead, the database itself holds the rules: "you may read your own rows, and nobody else's."

The rules live on the table, so it does not matter what the browser asks for. A request for someone else's data returns nothing, because the database refuses, not because the app was polite enough not to ask.

This immediately created a problem that teaches the whole concept:

Symptom
With "you can only read your own rows" in place, the leaderboard was empty. Correctly — a leaderboard is by definition other people's rows.
Cause
The rule is right for the table and wrong for this one feature. Loosening it would expose every column of every player's record to satisfy a page that needs two.
Fix
A view — a saved query that runs with the privileges of whoever defined it rather than whoever calls it. It exposes exactly username and score, nothing else. The underlying table stays locked. The public gets a window, not a door.

The same shape solved usernames. "Is this name taken?" cannot be answered by letting the browser read the users table. Instead a small database function takes a name and returns only a boolean. You learn whether it is free; you learn nothing about who has it.

The key that is supposed to be public

Supabase gives you two keys, and the difference matters more than almost anything else here:

Supabase keys
KeyWhere it goesWhy
anonIn the browser bundle. Public by design.It identifies the project, not a person. Every rule above still applies to it. Anyone can read it out of the JavaScript, and that is fine.
service_roleNowhere in this project. Ever.It bypasses every rule. In a browser bundle it hands the entire database to anyone who opens devtools.

Worth internalising: the anon key being visible is not a leak, and treating it as one leads people to hide it in ways that break the app. The security is the row rules, not the secrecy of the key.

Symptom
Sign-up appeared to succeed, then the app behaved as though nobody was logged in.
Cause
The code checked data.user?.id. With email confirmation switched on, Supabase returns a user but no session — the account exists, but nobody is signed in until the email link is clicked. A user object is not proof of a login.
Fix
Check data.session?.user?.id instead. The session is the thing that means "signed in right now".

The terms for it

Row Level Security (RLS) — per-row access rules enforced by the database. Policy — one such rule. SECURITY DEFINER — the view/function property that makes it run with its creator's privileges. RPC — calling a database function directly. Principle of least privilege — the boolean-only username check. Session versus user — the bug above.

Leg 07 · Deploy

Shipping it

From a folder on your laptop to a URL anyone can open.

In plain words

Running npm run build produces a folder of plain HTML, CSS and JavaScript. Hosting is just putting that folder on a machine that answers web requests. Vercel does one extra useful thing: it watches your GitHub repository, and every time you push, it rebuilds and republishes automatically.

The one piece that does not come from the repository is configuration. The Supabase URL and key are read from environment variables — values supplied from outside the code — so they are set in Vercel's dashboard rather than committed. In this project they happen to be safe to publish anyway, but the habit is what matters: configuration is not source code, and the day you have a genuinely secret value you want that separation already in place.

Vite requires such variables to be prefixed VITE_ before it will expose them to browser code. That prefix is a safety catch — it forces you to state, explicitly, that a value is meant to be public.

The terms for it

Static site — no server-side computation per request. CI/CD — the push-triggers-build-and-deploy pipeline. Environment variable. Twelve-factor config — the principle that configuration lives in the environment, not the codebase. Preview deployment — the throwaway URL Vercel builds for each branch.

Leg 08 · CSS

The button that turned white on white

The best bug in the project, because the cause is a rule most people have never heard of.

Before we started

With the game working, attention turned to how it looked — and to a request to ignore the plan's design section entirely in favour of something with more atmosphere. Then the main call-to-action went invisible.

Symptom

The "Play today" button rendered white text on a white background. The utility classes setting its colour were present in the markup and simply not applying.

color:    rgb(237, 239, 243)  ← same
bgcolor:  rgb(237, 239, 243)  ← same
fontSize: 16px   (expected 17)
weight:   400    (expected 500)
Cause

A plain reset rule in the stylesheet:

button { font: inherit; color: inherit; }

In Tailwind v4 every utility class lives inside a cascade layer. The rule that catches people: any CSS outside a layer beats all CSS inside one — regardless of specificity, regardless of source order. A bare one-word selector was outranking every utility in the framework.

Fix
Move the resets into @layer base. Now they are layered too, they sit below the utilities, and normal cascade rules resume.

In plain words

CSS layers are a way of saying "this whole group of styles is lower priority than that group" — useful for keeping a framework from fighting your own code.

The counterintuitive part is what happens to styles in no group at all. You would guess they are neutral. In fact they win over everything in every group. Opting out of the system does not make you a citizen; it makes you king.

A second, smaller v4 change surfaced the same week: buttons stopped showing a pointer cursor on hover, because v4's reset no longer sets cursor: pointer on them. The fix was trivial; finding it was not, because "the buttons don't feel like buttons" is a feeling, not an error message. We audited all 200 interactive elements on the page to be sure none were missed.

The terms for it

Cascade layers (@layer) — the mechanism. Unlayered styles — the ones that outrank everything. Specificity — the usual tie-breaker, which layers override entirely. Preflight / CSS reset — the baseline styles a framework applies. Computed style — what the browser actually resolved, which is what you inspect when the markup looks right and the pixels are wrong.

Leg 09 · Typography

The numbers that looked wrong

A report of "too small" that was not about size at all.

Symptom
"The numbers are a little smaller to look at." Measuring them found the font size correct and matching the surrounding text.
Cause
The display face, IM Fell English, uses old-style figures — digits designed to sit at the height of lowercase letters, with some descending below the baseline. In a book they are beautiful. In FLAG 1 OF 3, set in capitals, the 1 and 3 sit visibly low and small: FLAG ₁ OF ₃. Nothing was smaller. The digits were a different kind of digit.
Fix

Any label containing a number gets set in Archivo, whose figures are uniform and full-height.

/* Same ledger treatment, but in Archivo — IM Fell's old-style
   figures turn "Flag 1 of 3" into "Flag ₁ of ₃". */
.ledger-num {
  font-family: var(--font-sans);
  font-variant-numeric: tabular-nums;
  letter-spacing: 0.18em;
  text-transform: uppercase;
}

This one recurred. It was diagnosed and fixed for one label, then appeared again later in a different component that had used the original class. The lesson is that a fix expressed as a reusable class only helps where someone remembers to use it — and the more durable version of this fix would have been to change the font stack for all numeric labels at once.

In plain words

When a person says something looks wrong, they are reliable about the symptom and unreliable about the cause — and that is not a criticism, it is just what it is like to look at a screen. "Too small" was a completely accurate description of the experience and a completely wrong diagnosis. Measure before you act on the stated cause.

The terms for it

Old-style (text) figures versus lining figures. Tabular versus proportional figures — tabular ones all share a width so columns align. x-height, baseline, descender. font-variant-numeric — the CSS property that controls all of this when a font offers both sets.

Leg 10 · Layout

The menu that flew off the screen

"Fixed to the screen" turns out to have an asterisk.

Symptom
On a phone, the country picker's sheet — pinned to the bottom of the screen — rendered at top: -159px, above the visible area entirely.
Cause

position: fixed normally means "position me against the browser window". But if any ancestor has a transform, a perspective, or transform-style: preserve-3d, that ancestor silently becomes the reference frame instead.

The flag card flips in 3D on reveal. The picker was nested inside that flip. So "fixed to the screen" quietly meant "fixed to the flipping card".

Fix
Move the picker out of the flip entirely — and leave a comment at both ends, because the two pieces of code look unrelated and someone will otherwise nest them again.

src/components/Round.tsx

{/* Outside the flip on purpose — `perspective` and `preserve-3d` both
    make an element the containing block for position: fixed, which
    would drag the picker's mobile sheet off the viewport. */}

The paired comment sits above the flip itself, warning against putting anything between it and the picker. A bug whose cause is action at a distance needs its warning at the distant end, not only at the scene of the crime.

Then the keyboard opened

In plain words

A phone has two ideas of "the screen". One is the whole window, which does not change when the on-screen keyboard appears. The other is the part you can actually see, which shrinks by the height of the keyboard.

"Stick to the bottom" uses the first one. So the sheet dutifully stuck itself to the bottom of the window — underneath the keyboard, invisible.

The browser exposes the visible one separately. The difference between the two is exactly how much the keyboard is covering:

src/hooks/useKeyboardInset.ts

const covered = window.innerHeight - vv.height - vv.offsetTop;
setInset(covered > 24 ? Math.round(covered) : 0);

The > 24 is not arbitrary: browsers report small fluctuations of a pixel or two, and treating those as a keyboard would make the sheet twitch.

The terms for it

Containing block — the box an absolutely- or fixed-positioned element is measured against. Stacking context — a related trap the same properties create. Layout viewport versus visual viewport — the two screens. visualViewport API — how you read the second one. Action at a distance — a cause far from its effect.

Leg 11 · Constraints

When there is genuinely not enough room

Three attempts at one layout, and a lesson about which units know what.

With the sheet correctly above the keyboard, it collapsed to a sliver — just a search box, no list. The formula sizing it was:

maxHeight: calc(100svh - keyboard - 320px)
Symptom
On the reported phone that resolves to 44px — the input and nothing else. On a taller test device it left about 200px and looked fine, which is exactly why it shipped.
Cause
svh is the viewport minus browser chrome — it knows nothing about the keyboard. So the keyboard was subtracted from a figure that had not accounted for it, and then another 320px was taken off for the flag. The keyboard was effectively counted twice.
Fix
Size against the visual viewport — the measurement that already excludes the keyboard — instead of mixing two unit systems that disagree about what a screen is.

That fixed the collapse and revealed the real problem: the sheet now had a sensible height and sat directly on top of the flag. Measuring the page showed why nothing could simply move out of the way:

docH: 711  ===  innerH: 711   the phone layout cannot scroll at all

So the arithmetic was fixed and brutal. Around 375px visible with the keyboard up, of which the flag is 180. The chrome above it — a 76px header and a 45px label — was consuming the rest.

Reclaiming the space
ElementBeforeAfter
App header76pxfolded away
Gap above flag20px8px
Flagcovered180px, visible
Sheetover the flag155px below it
Rows of results02

Two decisions inside that fix are worth more than the fix:

Measure, don't assume. Rather than hard-coding "the flag ends at 225px", the round measures the flag's actual bottom edge and hands the picker whatever is left. Constants like that drift the moment someone changes the header; a measurement cannot.

Name the cost out loud. The instruction had been "do not make the flag smaller". Honouring it means the list gets two rows and not four. That is a real cost, and the right move was to ship the version that respected the constraint and then say plainly what it cost — rather than quietly overriding the instruction, or pretending two rows was the ideal outcome.

The terms for it

Viewport units — vh, svh, lvh, dvh, each measuring a different idea of "the screen". Layout thrash — the reason measurement is deferred a frame. Progressive disclosure — chrome that steps aside when space is scarce. Design constraint — a rule you honour and cost out, rather than silently break.

Leg 12 · Architecture

Real facts, and the database we didn't build

The best architectural decision in the project was to delete most of the architecture.

Before we started

The request was: fetch fresh facts about each day's countries, save them to the database, and serve them from there. A reasonable design, and it implies a fair amount of machinery — a scheduled job, a server-side function, an API key, a shared table.

But the machinery only exists to solve specific problems, so it is worth asking which ones actually apply once you pick a source.

Why a server is usually needed — and whether it was here
Reason for a serverWith Wikipedia
Hide an API keyNot needed — the API is keyless
Get around browser cross-origin rulesNot needed — the API allows browser calls
Stop users poisoning shared contentNot needed — nothing is shared to poison

That third row is the interesting one. The vandalism risk only existed because of the shared table. A design where every browser fetches its own facts does not have that attack surface — the problem was created by the proposed solution.

In plain words

Each browser asks Wikipedia for the three countries directly, then keeps the answers in its own storage under today's date. Tomorrow is a different date, so it fetches again — once a day, three requests.

The cost is that each visitor makes three requests instead of everyone sharing one fetch. Wikipedia serves billions. This is noise.

What we avoided by not building it: deploying a scheduled function, wiring a cron job, and — the real hazard — reimplementing the daily-seed logic in a second language, where any drift between the two would silently pair the wrong fact with the wrong flag.

The part that needed real care

Wikipedia article titles are not country names. Left alone, this feature would have confidently told players about a US state, an island, and a river:

Ambiguous titles, and where they would have landed
CountryNaive titleCorrect title
Georgiathe US stateGeorgia (country)
Irelandthe islandRepublic of Ireland
Nigerthe riverNiger

Twenty titles are mapped explicitly, and a script checks all of them plus eight controls actually resolve to a country article — 28 / 28. The check tests the content, not just that a page exists: a summary that doesn't describe a place fails.

Finally, the whole feature is additive. If Wikipedia is unreachable, every fetch returns null and the game falls back to its built-in fact templates. Verified by blocking the domain outright: six requests aborted, the game showed "Kabul is the capital, and about 43.8M people live in Afghanistan", offered no link, cached nothing, and threw no errors. Hints were deliberately left offline-only and deterministic — they are gameplay, and gameplay must never depend on a network.

The terms for it

YAGNI ("you aren't gonna need it") — the principle behind not building the table. Attack surface — what the shared table would have added. CORS — the cross-origin rules that usually force a proxy. Cache key and invalidation — the date. Graceful degradation and progressive enhancement — the fallback. Single source of truth — why duplicating the seed logic was the real danger.

Because it is a real browser, it catches things that only happen in one — layout, fonts, animation, offline behaviour.

Two failures worth more than the passes

Symptom
Several tests failed after a change that was, in fact, correct.
Cause
The tests were wrong. They compared against text before CSS uppercased it, hard-coded a screen height of 780 when the browser reported 793, and expected a blur value that had been intentionally changed. A test asserting yesterday's truth fails loudly and points at the wrong file.
Fix
Assert against what the browser reports (window.innerHeight) rather than a number typed in once, and delete assertions describing behaviour that was deliberately removed.
Symptom
A script reported success while changing nothing. Four heading replacements never applied.
Cause
The search text had been normalised — double spaces collapsed — so it no longer matched the file. Find-and-replace with no match is not an error. It is silence.
Fix

Every editing script now asserts that each replacement matched exactly once before writing:

assert s.count(old) == 1, (s.count(old), old[:60])

This one line has caught real mistakes repeatedly since.

The general lesson: an operation that can quietly do nothing is more dangerous than one that fails. A crash tells you where to look. Silence lets you spend an hour debugging code that was never edited.

The terms for it

End-to-end (E2E) test — driving the real app as a user. Regression suite — the tests you re-run to prove old features still work. Headless browser — a browser with no visible window. Flaky test — one that fails for reasons unrelated to the code. Fail loudly / fail fast — the assertion above. Test fixture — the seeded state a test starts from.

Leg 14 · Second game

Placing a country on the map

A second game behind a toggle, where "how close were you" turned out to be the whole problem.

In plain words

A switch in the top bar flips between Flags and Map. In Map mode you are given five random countries by name, one at a time. You tap where you think each one is, lock the pin in, and the map zooms to show the real country, a dashed line to it, and your points: 5,000 for landing on it, fewer the further off you were.

It is deliberately walled off from the flag game — no daily seed, no streak, no sync. The only thing it remembers is your best score, in the browser.

Before we started

The map itself is drawn in code rather than from an image: country outlines come from a public atlas file and a projection library turns latitude and longitude into screen positions. Drawing it means the same code can answer the reverse question — "which latitude and longitude did the player just tap?" — which is exactly what scoring needs.

Two datasets that don't speak the same language

Our country list is keyed by two-letter codes (FR). The atlas is keyed by three-digit numeric codes (250). Nothing in either file connects them, so a small generated file does: one script pulls the same source dataset the country list came from and writes the code, numeric id and a centre point for all 195.

Which atlas resolution actually contains our countries
AtlasSizeCountries missing
Low detail (110m)108 kB29 — Singapore, Malta, Monaco, most small island states
Medium detail (50m)756 kB1 — Tuvalu

The smaller file would have silently made a seventh of the game unscoreable. The medium one is seven times larger, so it is loaded only when Map mode is opened — flag players never download it. Tuvalu, the one gap, falls back to distance from its centre point.

What "close" should mean

Symptom
The obvious rule — distance from the tap to the country's centre — punishes correct answers. A tap in eastern Siberia is inside Russia and still thousands of kilometres from Russia's centre.
Cause
A centre point stands in for a shape, and the bigger the country the worse the stand-in. Worse still, a check found 24 of the 195 centre points lie outside their own country's outline — mostly coastal and archipelago nations whose "centre" is at sea.
Fix

Score against the shape, never the centre. If the tap is inside the outline, the distance is zero. Otherwise it is the distance to the nearest point on the border. The centre is only used to draw a highlight ring, where being slightly off does no harm.

Distance is measured on the globe, not in screen pixels: the projection stretches the far north and south, so a pixel near Greenland covers far less ground than one at the equator.

Points fall away smoothly — 5000 × e−distance / 1500 km — so a near miss is worth nearly as much as a hit, and a guess on the wrong continent is worth almost nothing. Anything within 25 km of the border counts as exact, because a micro-state is a handful of pixels even zoomed in, and a tap is a fingertip wide.

A tap, a drag and a pinch start as the same event

On a touchscreen, placing a pin, panning the map and zooming all begin with a finger going down. The browser cannot know which one the player means until the finger moves or lifts. So the map watches: one finger that moves less than five pixels is a tap and drops the pin; anything more is a pan; a second finger means a pinch, and that gesture can never become a tap afterwards. Scroll-to-zoom needs a listener registered as non-passive, or the browser scrolls the page underneath the map at the same time.

Two smaller details keep zooming from looking wrong. Borders use a stroke that ignores the zoom level, so a 60× zoom doesn't draw borders 60× thicker. And the pin is scaled by the inverse of the zoom, so it stays the same size on screen while the world grows under it.

The terms for it

Map projection — flattening the globe, and its inverse, turning a screen point back into coordinates. Great-circle distance — distance along the Earth's surface. Point-in-polygon — the "is the tap inside the country" test. Join key — the shared field that links two datasets. Code splitting / lazy loading — shipping the atlas only to those who need it. Exponential decay — the scoring curve. Gesture disambiguation and touch slop — telling a tap from a drag. Passive event listener — one that promises never to cancel scrolling. Antimeridian — the 180° line that makes Russia and Fiji span both edges of the map.

The four habits worth keeping

  1. The symptom is rarely where the cause lives. A white button, a flying menu, small-looking numbers — none of the causes were in the thing that misbehaved.
  2. Measure before you believe anyone, including yourself. "Too small" was the wrong diagnosis. So was a test that hard-coded a screen height. So was a formula that looked correct on the only phone it was tried on.
  3. Comment decisions, not syntax. Every comment quoted in this log explains why — a dead API, a containing block, an alias that would have gone wrong. None of them explain what the line does.
  4. Prefer the design with fewer moving parts. The database that wasn't built could not go stale, could not drift from the seed logic, and could not be poisoned.
